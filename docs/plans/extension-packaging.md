# Extension Packaging

## Goal

Give every package that ships q rules one place to put them, and make a repo able to consume the rules it authors.

Two gaps close. A package's payload moves into a single `q-extension/` directory at its package root, so what ships is answerable by looking rather than by reading a whitelist. And the repo authoring those rules gets them into its own briefing, which no mechanism does today: an authored extension's conventions are groomed and held to the policy, but nothing routes a session to them.

The q pin returns to the repo root in the same change. Putting it in a workspace manifest is what left the session-start hook unable to find it at all (#82, closed in favour of this plan).

## Context

### What ships today, and how it is declared

- `package.json:5` lists six top-level directories in `files`: `conventions`, `skills`, `agents`, `hooks`, `references`, `.claude-plugin`. A seventh payload directory added without editing that line silently does not ship.
- `scripts/` and `tests/` are outside that whitelist, so nothing in them reaches a consuming project.
- `.claude-plugin/marketplace.json` is q's own bootstrap marketplace, named `q`, sourcing the plugin at `"./"`. `.claude/settings.json` declares that name and enables `q@q`.
- `scripts/manifests.mjs:15` names `.claude-plugin/plugin.json` as a version-carrying file. `package.json:10` runs `claude plugin validate --strict` against `.`, `skills` and `agents`.
- `hooks/session-start.mjs:86` reads the loaded q's version with `installedVersion(root)`, where `root` is `CLAUDE_PLUGIN_ROOT` and `installedVersion` reads `<dir>/package.json:version` (line 56). That works only because the plugin root and the npm package root are the same directory today. `package.json` must stay at the package root, so the payload move separates them.
- `tests/helpers.mjs:79-99` stages the hook pair by copying `hooks/session-start.sh` and `hooks/session-start.mjs` out of the repo root, and writes the fake plugin manifest to `<root>/package.json` — mirroring today's colocation rather than the split above. `tests/session-start.test.mjs`'s "q's own checkout" case passes `{ proj: repoRoot, root: repoRoot }`.
- `docs/guides/releasing.md:5` names the three version-carrying files, and line 27 commits `.claude-plugin/plugin.json` by that literal path. No check exercises the guide.

### Where the payload's location is written down

Each of these names a path into the package, or restates how one resolves:

- `conventions/documentation.md`, Package doc paths — a reference is "package name plus path from the package root", resolving "to the installed copy in `node_modules/`, or to the package's working tree in the repo that authors it".
- `docs/conventions/documentation.md:20` — "In this repo, `@lab43/q` in a path reference resolves to the repo root, q's own working tree."
- `CLAUDE.md:26` — the same claim, in the always-loaded briefing.
- `docs/conventions/skills.md:43` — framework docs are read from `node_modules/@lab43/q/conventions/`.
- `docs/conventions/skills.md:45` — a `.claude/skills/` skill reaches q's files by path form, "which resolves here to the repo root".
- `references/agent-briefing.md:20` — the template every consuming project's `CLAUDE.md` carries hardcodes "`@lab43/q conventions/principles.md` is `node_modules/@lab43/q/conventions/principles.md`".
- `references/enforce-pins.md:6`, `README.md:15`, `README.md:203`, `skills/install/SKILL.md:77`, `docs/guides/driving-manual.md:11,13`.
- `docs/guides/driving-manual.md:21` — the expected skill count is "the number of directories in `skills/`".
- `README.md:211` and `docs/guides/driving-manual.md:29` — both reclaim this repo's dev marketplace with `claude plugin marketplace add --scope local ./`, naming the repo root as the directory holding `.claude-plugin/marketplace.json`.

### How extensions are found and pinned

- `hooks/session-start.mjs:71-74` reads `devDependencies` only, and so do `skills/update/SKILL.md:12` and `skills/sync/SKILL.md:27`. `references/agent-briefing.md:54` says "direct dependencies" without restricting the map, so it is ambiguous rather than wrong. A package depended on for its code is a regular dependency, so as an extension it is invisible to the first three.
- `skills/uninstall-extension/SKILL.md:16-18` identifies an extension from `node_modules/<extension>/package.json`, the registry, or a watermark entry, never from a dependency map — so Decision 4 leaves its identification alone. Its Step 3.1 is another matter: it runs `npm uninstall` on the target, which was safe only while an extension was a package nothing imported.
- `conventions/extensions.md`, Pinning, makes the project's live q pin and the extension's written-against declaration one field — "never two to drift apart". That is what puts the pin in a workspace manifest in a monorepo. `references/q-state.md:7` restates it as "one exact devDependency for q and one per installed extension".
- `conventions/extensions.md`, Description, makes `package.json`'s `description` the heading a consuming project's briefing gives an extension's index lines: "One sentence serves the session reading that briefing and the registry's readers alike." q itself does not follow it — `package.json:4` is the framework blurb while `references/agent-briefing.md`'s template carries a different heading for q's group, kept in sync by hand, with line 50 carving out why: "q's group takes the heading spelled out above."
- `conventions/extensions.md`, Identity, rules that q is not an extension and carries no keyword. `docs/plans/single-npm-package-and-extensions.md:103` records why, as an amendment written during implementation: the category "bought no uniformity in practice — the hook still needed a dedicated `@lab43/q` branch, `/q:uninstall-extension` still refused q by name, and Pinning still exempted q from carrying a q pin."

### What has no mechanism

- `conventions/extensions.md`, Authoring, puts an authored extension's `conventions/` on its repo's documentation surface, and `skills/groom-docs/SKILL.md:22` grooms them. Nothing indexes them. `references/agent-briefing.md:54` indexes the project's dependencies, and a repo is not its own dependency.
- `conventions/extensions.md`, Graduation, moves conventions out of `docs/conventions/` into the extension. `docs/conventions/` is indexed and the authored extension is not, so graduating a rule removes it from the briefing.
- `docs/conventions/documentation.md`, The tier test, decides which of two homes a rule goes to. It is written for q alone. `CLAUDE.md:7` cites it by a source marker, and `CLAUDE.md:9` tells every session to apply it at that path. `README.md:201` carries the same marker.

### Verified Claude Code and npm behavior

Established with throwaway fixtures against CLI 2.1.236, npm 11 and Node 24, because none of it is readable from this repo. `docs/plans/single-npm-package-and-extensions.md:37-52` records the earlier round; these are the facts this plan adds.

- A marketplace manifest at a package root whose plugin `source` is a subdirectory passes `claude plugin validate --strict`, and components under that subdirectory validate.
- `claude plugin marketplace add --scope local` then `claude plugin install --scope project` both succeed against such a plugin, and a session loads its skill under full namespacing — `qfix:hello` from a plugin rooted at `<package>/q-extension`.
- `npm pack` ships the whole payload tree from a single `files` entry, and preserves the executable bit on a hook nested inside it.
- `claude plugin install --scope project` writes `enabledPlugins` into the project's tracked `.claude/settings.json` and reformats the whole file. `skills/install/SKILL.md:84-95` already writes those keys by hand rather than shelling out; this is the reason.
- A package whose `files` whitelist does not name the payload directory ships none of it, silently. A fixture carrying the `q-extension` keyword, a `q-extension/conventions/naming.md`, and `files: ["dist"]` packs two files — `dist/index.js` and `package.json`. The published package announces itself as an extension and contains no rules. Most published libraries carry a `files` field, so this is the common case rather than an edge one.

### Constraints

- No project outside this repo has q installed (the user's ruling, 2026-09-20). npm carries 0.4.0 and 0.5.0, both published 2026-09-19. No migration or compatibility path is needed.
- `hooks/hooks.json` invokes `session-start.sh` directly rather than through `bash`, so the file must stay executable in the tarball.
- `${CLAUDE_PLUGIN_ROOT}` resolves to the plugin's source directory (source: `docs/plans/single-npm-package-and-extensions.md:44`). Moving the plugin root moves the variable with it, so no skill's `${CLAUDE_PLUGIN_ROOT}/references/…` reference changes.

## Decisions

1. **One `q-extension/` directory at each package root carries the whole payload.** It holds `conventions/`, `references/`, `skills/`, `agents/`, `hooks/` and `.claude-plugin/`, and becomes the plugin root. `files` shrinks to `["q-extension"]`.

   What ships stops being a list to maintain and becomes a location: a payload file is one under `q-extension/`. Today's six-entry whitelist fails silently when a seventh directory is added. And a package that is a product as well as an extension — a component library shipping its own conventions — gets one directory beside its `src/` instead of six generic names squatting on its repo root.

   npm requires `package.json` at the package root, so the plugin root stops being the package root and sits one level below it. Anything reading one while meaning the other breaks, and the hook's version read is exactly that (Phase 4).

   `docs/plans/single-npm-package-and-extensions.md:66` rejected this: "a package under `packages/q/`. It makes the publish boundary structural rather than declarative, which is a real advantage, but it relocates every skill, hook, agent and reference to buy it." Both grounds have shifted. The advantage it names is now the point, and extensions need a payload directory whether or not q adopts one — uniformity is a new benefit that was not on the table. The cost is also smaller than it reads: skills reach their references through `${CLAUDE_PLUGIN_ROOT}`, which moves with them, so directories move and references do not. That rejection was also about a nested npm package; this is a directory inside the one package, which keeps the single-version property the decision was protecting.

2. **The name is `q-extension`, matching the keyword.** `conventions/extensions.md`, Identity, already makes `q-extension` the identity of a package carrying q rules. The directory holding what the keyword promises takes the same name (source: @lab43/q conventions/writing.md, One name per concept).

   Inside q the name is mildly wrong, because q is not an extension. That is accepted rather than worked around: the name is read by every extension-authoring repo there will ever be and by q's own maintainers, and optimizing for the many is the better trade. `docs/conventions/documentation.md`, Working on the payload, already records that q follows the extension authoring rules without being an extension; the naming call is recorded there as one more clause on that ruling.

   Rejected: a different directory name inside q. It buys a name that is never wrong and costs a permanent `if package is @lab43/q` in every rule and check that resolves a package path, which is the opposite of the uniformity this plan is for.

   Rejected: `package-docs`. It reads as inert, and the directory holds `hooks/session-start.sh`, which executes at every session start. `docs/plans/single-npm-package-and-extensions.md:24` records this repo being caught by that assumption once already: the old rule required "documentation and nothing executable", which line 102 records becoming false once the hook shipped in the package.

3. **A package-prefixed reference resolves under that package's `q-extension/`; a bare path is repo-relative and literal.** `@lab43/q conventions/writing.md` resolves to `node_modules/@lab43/q/q-extension/conventions/writing.md`, or to `q-extension/conventions/writing.md` in the repo authoring it. `docs/conventions/testing.md` means exactly that path from the repo root.

   The payload directory therefore never appears in a marker, and every marker on the surface today survives the move unedited. The rule is one sentence in the doc a reader already consults for marker grammar, and it applies to q and every extension identically.

   Three sites restate the old resolution and become false: `docs/conventions/documentation.md:20`, `CLAUDE.md:26`, and `docs/conventions/skills.md:45`. Each is corrected, not supplemented.

   Rejected: spelling the segment literally, as `@lab43/q q-extension/conventions/writing.md`. It rewrites every marker in the repo to buy a path a reader can follow without knowing one rule, and it reads as a stutter for q specifically.

   Rejected: implying `docs/` for bare paths too, for symmetry. `conventions/documentation.md`, Markers, lets a marker target any repo file — `CLAUDE.md` points at both `docs/conventions/documentation.md` and `.github/workflows/checks.yml`. A bare path would then mean two different things with nothing to distinguish them, and rescuing it needs a list of privileged prefixes, which `docs/conventions/documentation.md`, Structure is earned, rules out.

4. **Extensions are discovered in `dependencies` as well as `devDependencies`.** A product package carrying conventions is depended on for its code, so it is a regular dependency. Discovery keys on the `q-extension` keyword, which already identifies the package, not on which dependency map holds it.

5. **The project's live q pin is always the repo root's `package.json`.** Nothing locates it and nothing may move it. A repo authoring an extension pins q at its root like any other q consumer.

   This is what closed #82 rather than the locator PR #112 built. With every package's payload at its own package root, the single-package case puts the pin and the declaration in the same file anyway, so the locator solved a problem the layout removes.

6. **An extension's payload sits at its own repo's root, so the pin and the written-against declaration are one field by construction.** q's machinery supports a package whose root is its repo root: an extension-only repo, or a product package that also ships rules. The root `package.json` then holds both the project's live q pin and the declaration telling consumers which q version the rules were written against, because there is only one manifest for them to live in.

   `conventions/extensions.md`, Pinning, already demands one field — "never two to drift apart". What broke was that the rule had to *force* the pin somewhere to get it, and in a monorepo that somewhere was a workspace manifest the hook could not find (#82). The layout now makes the rule true for free, so nothing has to force anything and no check has to enforce it.

   A repo publishing an extension from a sub-package keeps working as a publisher — the tarball is an ordinary package with the keyword and a payload directory, and consumers install it normally. What is unsupported is q's integration inside that authoring repo: nothing holds the sub-package's declaration equal to the repo's q pin, and nothing indexes its conventions in that repo's own briefing (see: Out of scope).

   Rejected: supporting sub-package extensions with a declaration-equality check. It needs a home that reaches consuming repos — `scripts/` is outside the `files` whitelist and would run only in q's own repo — and the natural home, the session-start hook, would need `fs.globSync` to enumerate `workspaces` patterns, putting a Node 22 floor under a hook that must never crash. Two supported shapes that both put the package root at the repo root remove the need entirely.

7. **A repo's own payload conventions get their own briefing group, shaped like an installed extension's, unpinned and unwatermarked.** The group is read from the working tree and headed the same way a consumed extension's is — by `q.description` (Decision 10). No pin, because a repo does not depend on itself; no watermark, because a watermark certifies that rule changes have been absorbed and there is nothing to absorb in rules you are editing (source: @lab43/q conventions/extensions.md, Authoring — "Don't record a deviation from a convention you ship — edit it"). *(deviation: that rule was deleted on the user's ruling, so this citation no longer resolves to text. Its general half — a project may override a rule it consumes — is what `documentation.md`, Three tiers of conventions already carries, and `/q:groom-docs`'s cross-tier sweep escalates a conflict to the user either way. The special case forbade a legitimate one: a single site excused by an exception marker. The unwatermarked group stands on its own reason, which is that a repo does not depend on itself.)*

   Shaping it like an extension's group is what makes the author's briefing show what their consumers' briefings will show. The rules they ship sit under the same heading, in the same form, as they will in every project that installs them.

   It also makes graduation legible. A rule graduating out of `docs/conventions/` into the payload moves its index line from the project's group to the payload's — it changes which rules it sits among, and stops being a project ruling the moment it lands. Without the payload group it would simply leave the briefing, which is how graduation currently loses rules.

   The session-start hook needs no change for this. Every check it runs walks dependency entries by name, and a package is never its own dependency, so the repo's own payload is already outside its reach.

8. **Watermarks keep tracking package versions.** With conventions riding in a product package, its version moves for product reasons, so a release touching no rules still moves the pin past the watermark and the hook goes loud until someone runs `/q:update` to find nothing to reconcile.

   That cost is accepted rather than engineered around. A fingerprint of the shipped conventions would remove it, at the price of a watermark no human can read in a diff and something to compute it — either the hook on every session start or a publish-time build step, which `docs/plans/single-npm-package-and-extensions.md:96` already rejected for `plugin.json`'s version. `docs/conventions/documentation.md`, Structure is earned, says to ship the plain version until it demonstrably fails, and with no consumers the failure is hypothetical.

9. **The tier test becomes framework law, rewritten rather than moved, keeping its heading.** Every extension-authoring repo now has the two homes q has: a payload that ships and binds consumers, and `docs/conventions/` governing work on the repo itself. The rule deciding which home a rule goes to therefore binds consumers, so it belongs in the payload.

   It is rewritten, not relocated. The existing text names `@lab43/q` and q's own directories, and the rule it carries says payload "is addressed solely to consumers" and must never mention q's own repo — so a verbatim move produces a payload doc breaking its own rule on arrival. The generalized rule names the two homes by their roles; q's tier keeps only what is true of this repo alone.

   The heading stays "The tier test" in its new home, so every existing marker changes only which file it names, never which section. *(deviation: it landed in `conventions/extensions.md` as "Which rules ship", not in `documentation.md` under its old heading. Two things showed the planned home was wrong once the rule was generalized. The section had to open by telling most of `documentation.md`'s readership — every project that consumes rules without publishing any — that it did not apply to them; a section that excludes its doc's audience in its first sentence is in the wrong doc. And "tier" then meant two different things three sections apart, since Three tiers of conventions names an axis across packages while this rule names one inside a single repo. `extensions.md` is addressed to extension authors already, which scopes the rule by topic instead of by disclaimer, and puts it beside Layout. Every referrer changed file and section together.)* *(deviation: Graduation was then merged into it and the heading deleted. The two sections asked one question with two different tests — "has the audience grown beyond one project" against "would this change what a session in a consuming repo writes or flags" — and `documentation.md` routed to only one of them. Graduation survives as the clause about a rule passing the test later.)* *(deviation: the rule also gained a guard the plan did not foresee — whether a repo publishes rules at all is the user's decision, and a session that judges a rule has outgrown the project says so rather than creating a payload to hold it. The graduation rule took the same guard, having read as a condition that fires rather than a call someone makes.)*

   Rejected: leaving the rule in q's tier and writing a second generalized copy into `conventions/extensions.md`, Authoring. Two homes for one rule is the duplication the policy forbids, and the copies drift.

10. **A `q.description` field in `package.json` carries the extension's rules blurb, and q uses it too.** A consuming project's briefing heads an extension's group of index lines with a description of what its rules govern. `package.json`'s own `description` served that when an extension was a dedicated conventions package, because both audiences wanted the same sentence. A product package that also ships rules has two audiences wanting different ones: the registry wants what the library is, the briefing wants what the rules cover.

    It is required of every package carrying the keyword, and never falls back to `description`. *(deviation: neither clause shipped in `conventions/extensions.md`, Description. The no-fallback rule went to `references/agent-briefing.md`, which decides how a group is headed and already had to say what a package shipping no `q.description` gets — stating it in both places was one fact with two homes. What Description keeps is the author-facing half: what the field says, and what to write in it. The explicit requirement came out with the rest: a missing field costs a name-only heading and a `/q:install` report, which is pressure enough without declaring a required field.)* A fallback degrades silently: an author who does not know the field exists gets a registry blurb heading a conventions group, sees nothing wrong, and every consuming project inherits it. Requiring it also makes an existing rule enforceable — Description already says to "Name the territory the rules cover, not the package's shape", which today competes with what the registry wants from the same field and loses.

    Absent, the group falls back to a heading of the package name alone, which `references/agent-briefing.md:50` already specifies for a description-less extension. `/q:install` reports the omission on an extension run so the consuming project can raise it with the author; it does not refuse the install, since an extension missing a blurb is otherwise working. `/q:groom-docs` already checks this field for the payload a repo authors (`skills/groom-docs/SKILL.md:32`) and checks the new one instead.

    Rejected: falling back to `description`. It costs a dedicated conventions package one duplicated line to avoid, and buys a silent wrong heading in the case the field exists for.

    q adopts it rather than staying special. q already has the two-audience split and resolves it by hardcoding: its `description` is the framework blurb, while `references/agent-briefing.md`'s template carries a separate q heading and the carve-out that makes it work — "q's group takes the heading spelled out above". With `q.description` set, that heading and that carve-out both come out, and every package's group heading comes from one place.

    `conventions/extensions.md` rejects "a `q` metadata key in `package.json` (configurable paths, a per-doc manifest) — every job it would do is already covered by the two directories above, the keyword, and the doc intros, and an enumeration of docs rots against its own contents." Both jobs it names are enumerations, and that objection still stands. Rewrite the rejection rather than delete it: the key carries the description and never a path, a doc list, or anything the directories and the keyword already answer.

    Rejected: writing one sentence to serve both audiences. It costs every extension-bearing product package a contorted registry description, on the field npm shows readers first.

    Rejected: taking the heading from a `q-extension/README.md` intro. It needs a required file where a field does, and a README is prose a human edits for humans, not a value a briefing restates verbatim.

11. **Catching up an out-of-band pin move becomes `/q:update`'s dominant path, and its framing says so.** Nobody runs a q skill to update a UI library; they run `npm install`, and the rules ride along. Update's pin-moving half survives only for packages a project pins deliberately — q itself, and dedicated conventions extensions — while its catch-up half becomes what most runs do.

    The routing already handles it and does not change. `skills/sync/SKILL.md:31` sends a pin differing from its watermark to `/q:update` bare, and `skills/update/SKILL.md:29` reconciles it "without moving any pin". So `/q:sync` after an `npm install` is the flow, and it works today. What changes is only which case update presents as typical: its description names catch-up last, and a description is all a session sees before choosing the skill.

    Rejected: moving reconciliation into `/q:sync`, so one skill covers the whole post-install flow. Sync has no delivery shape to reconcile with — `skills/sync/SKILL.md:8` says it "delivers no repo change, so there is no branch, review mode, or PR" — and `:35` forbids it outright, sourced from `references/q-state.md:29`: "watermarks certify reconciliation, and sync never reconciles." Reconciliation is doc editing that ships as a PR. Giving sync that shape is a redesign of both skills and wants its own plan.

12. **Watermarks stay in `.claude/q-state.json`.** They are the opposite kind of data from `q.description` on both axes that decide the file. The description must ship and is hand-authored; the watermarks must not ship and are machine-written.

    `package.json` ships whole and a field cannot be excluded from a tarball, so watermarks placed there would publish a project's own reconciliation state to every consumer of an extension it authors. `references/q-state.md` guarantees the opposite today: "The file never ships in an extension: it lives in `.claude/`, outside the `files` whitelist a tarball is built from." That file's own `note` also reads "Never edit by hand", while `package.json` is reserialized by npm on install and is already a high-traffic merge surface — the one-key-per-line diff a watermark move produces survives only in a file q owns.

    The line to record: what ships and is authored goes in `package.json`; what is machine-written and project-local stays in `.claude/`. *(deviation: the recorded line drops shipping and divides on who writes the file. Shipping does not separate the two — packages ship `scripts`, `devDependencies` and tool config as a matter of course, most q projects publish nothing at all, and a watermark that did ship would land unread under `node_modules/`. What does separate them is that the manifest is hand-authored and npm's to rewrite, while watermarks are machine-written into a file q owns outright.)*

13. **Single PR.** The change is borderline against `conventions/plans.md`, Delivery shape, which sets roughly a few hundred changed lines as one sitting. Most of the diff's size is Phase 1's `git mv`, which carries no content change and lands as its own commit so a reviewer can skip it. The rest of Phase 1 is the handful of edits without which the move ships broken, committed separately from the rename.

    Rejected: stacking. The phases after the move are small and every one depends on it, so a stack would be four thin layers on one large mechanical base, each waiting on the one below.

## Out of scope

- **Loading the skills, agents and hooks a third-party extension ships** — deferred to issue #115, inherited from `docs/plans/single-npm-package-and-extensions.md`. `conventions/extensions.md`, Layout, lets an extension ship a plugin of its own, but a project's marketplace manifest carries one entry, q's, and `skills/install/SKILL.md:124` says so outright: "Installing an extension's plugin is not yet part of this step." So such an extension is pinned, watermarked and indexed while its skills never load anywhere.

  This plan touches that gap from both sides without closing it. It makes the gap likelier to be met, because a product package can now be an extension and may ship a skill beside its conventions. It also makes closing it cheaper: the entry such an extension needs points at `./node_modules/<package>/q-extension`, the nested plugin root Decision 1 already establishes and this plan verified.
- **Precedence among extensions** — deferred and untracked, inherited from the same plan. Nothing here creates the conflict.
- **Rethinking which setup skills exist** — deferred to issue #116. Decision 11 reorders `/q:update` to lead with catching up an out-of-band move. `/q:install` and `/q:uninstall-extension` have the same shape and keep it here. The open question behind all three is whether they should stay directly invocable at all, once a developer reaches every one of them by running npm and then `/q:sync`. Nothing breaks either way — the routing resolves every case today — so this plan reorders one skill's framing and leaves which skills exist to be settled whole.
- **Keeping a package's code while declining its rules** — deferred. Decision 4 lets a package be both a dependency the project builds on and an extension, so "stop consuming these rules" and "remove this package" come apart for the first time. Phase 5 stops `/q:uninstall-extension` doing the second when asked for the first, which is as far as this plan goes. Declining the rules outright needs an opt-out the session-start hook can read: drop the watermark and its reverse-direction check fires on a keyword-carrying dependency with no entry, keep the watermark and the briefing disagrees with the record. That is a mechanism to design, not a step to add.
- **Extensions published from a sub-package of their authoring repo** — deferred. Publishing one still works; what is missing is q's integration inside that repo (Decision 6). Supporting it means holding each sub-package's declaration equal to the repo's q pin and indexing its conventions in the repo's own briefing, both of which need workspace enumeration that neither the hook nor a shipped script can do well. Adding it later is additive, not a migration.
- **A fingerprint watermark** — declined, per Decision 8. The cheaper fallback, if the no-op reconciliation run proves painful, is letting `/q:sync` move a watermark when the diff shows the conventions unchanged. That contradicts `references/q-state.md`'s "sync reads and compares; it never writes", so it is a decision to reopen deliberately, not a tweak.
- **Reopening whether q is an extension** — declined. Decision 2 takes the name without the category, and the amendment at `docs/plans/single-npm-package-and-extensions.md:103` recorded concrete evidence against the category.

## Phases

### Phase 1: Move the payload

Relocation, plus the one sentence that makes the moved paths resolve. Nothing else changes content.

1. `git mv` `conventions`, `references`, `skills`, `agents`, `hooks` and `.claude-plugin` into a new `q-extension/`.
2. `q-extension/conventions/documentation.md`, Package doc paths: a package-prefixed reference resolves under that package's `q-extension/` (Decision 3).
